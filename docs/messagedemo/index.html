<drupal-message> custom element demo

Approach: <drupal-messages> is a persistent container — always present, always empty between requests, stable htmx target. <drupal-message type="..."> is the individual item — server-rendered, delivered by <hx-partial hx-target="drupal-messages">, owns announcement, close wiring, and auto-dismiss. No JS message registry, no Drupal.Message class, no JS-constructed HTML. Type styling is pure CSS attribute selectors — no per-type container grouping needed.

Open the browser console to see announce calls that would go to Drupal.announce() in a real Drupal page.

Append — hx-swap="beforeend"

Each button appends a new <drupal-message> into the container. Messages accumulate — click multiple times or mix types.

Multiple messages in one response

One server response emits three <hx-partial> tags — two errors and a warning. Each lands as a separate <drupal-message> in order. connectedCallback fires on each and announces them individually.

Replace — clear then append

Two partials in one response: first hx-swap="innerHTML" with empty content clears the container, then hx-swap="beforeend" appends the new message. The server decides — no JS flag needed.

Server-driven clear

Single partial with hx-swap="innerHTML" and empty content. All <drupal-message> children are removed. disconnectedCallback fires on each, clearing any auto-dismiss timers.

Auto-dismiss — data-auto-dismiss

connectedCallback reads data-auto-dismiss and sets a setTimeout. The element self-removes after the delay. disconnectedCallback clears the timer if the element is removed earlier by a close click or a server clear.

Piggyback on any response

The message partial is independent of the main content swap. The response updates #demo-content via one partial and delivers a message via another — the server appends both to the same response body. The trigger button knows nothing about either target.

This area will be updated by the main content swap.

Full page load

On a full page load the server pre-populates <drupal-messages> directly in the HTML — no htmx, no partials. connectedCallback fires on each <drupal-message> as the browser parses the page, same code path as the htmx delivery.
